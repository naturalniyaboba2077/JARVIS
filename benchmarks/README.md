# Сравнение небольших моделей для Jarvis

Раунд v3: 8 тегов действий, 9 отдельных реплик с историей, 7 последовательных
реплик про юмор, 6 проектных задач, два seed. Новые фиксированные сценарии:
отклонение похожего проекта, уточнение про пустой список, пересказ двух заданных
синтетических источников, правка скидки после длинного префикса, исправление
среднего на пустом списке и анализ вложенного JS. Они добавлены до сравнительного
прогона и отделены от прежних задач; это не утверждение об отсутствии таких задач
в обучающих данных модели. Тексты с example.test — фикстуры, не реальные источники.

Новый агент сам вызывает проверку после записи. В стенде **обе** возможности
исполнения (`run_command` и `_verify_project`) заменены ограниченной проверкой
AST. Ни модельный shell, ни сгенерированный Python не запускаются. Корректный
код за пределами поддерживаемого подмножества AST считается неподтверждённым,
а не автоматически неверным. Настоящий unittest runner отдельно покрывается
доверенными ручными фикстурами в test_project_workflow.py.

Для проектов измеряются фактическая находка/правка, сохранность соседнего кода
и файлов, автоматическая проверка и полнота отчёта. `read_code` включает
автоматически подготовленный фрагмент: это доступность кода модели, не доказательство
его понимания. Сумма булевых checks не является единым баллом интеллекта. Тексты
и отчёты нужно читать вручную. В JSON записаны хеши исходников и кода стенда.

Каждый вид проектной задачи рекомендуется запускать отдельным процессом через
`--only projects --project-case CASE --repeat 2`, чтобы зависший HTTP-worker
предыдущей задачи не занял inference-slot следующей. Отчёт данного раунда:
PROJECT_WORKFLOW_2026-09-07.md. Предварительный CRLF-пилот не входит в итоговые баллы.

Стенд сравнивает локальные GGUF-модели на типах поручений из диалогов 6–7
сентября: поиск, чтение файлов, проверка проекта, продолжение разговора,
подтверждение похожего проекта, ошибки распознавания слова «анекдот» и юмор.
Имена и содержимое проектов заменены вымышленными. Архив не исполняется.

## Методика

- Один и тот же код Jarvis, реальные шаблоны разговоров и тегов действий.
- Настоящий `project_agent.run_project_agent` на искусственных проектах.
- Сеть inference ограничена localhost, облачного резерва нет.
- Теги проверяются, но не исполняются. Проектные чтение/запись ограничены
  временной копией; вместо shell работает доверенная проверка AST фикстуры.
- Новый временный каталог и память для каждого прохода. Настоящие настройки,
  журнал, проекты, микрофон, TTS, браузер и сообщения пользователя не трогаются.
- Все кандидаты сравниваются с одинаковым контекстом и параметрами загрузки.
  Seed фиксирует запрошенную случайность, но не обещает битовую воспроизводимость.
- Записываются полный ответ, tool calls, ошибки, finish_reason, расход токенов,
  время первого текста и первого фрагмента для TTS, а не время реального звука.
- Юмор оценивается отдельно человеком: непустой ответ не доказывает, что смешно.
- Скорость Windows/RTX не выдаётся за скорость Orange Pi. Размер GGUF не равен RAM.

Пример после загрузки модели с отдельным идентификатором:

```powershell
python -u -B benchmarks/model_compare.py --model jarvis-bench-example --label example --repeat 2
```

Результаты: `logs/model_comparison/`, вне Git. Основной запуск не меняет режим
рассуждения сервера, как текущий Jarvis. Опция `--reasoning-effort` предназначена
только для отдельно обозначенных экспериментов: принятие параметра сервером
не доказывает отключение thinking. Значение `off` этот LM Studio отвергает.

Основной прогон: контекст 8192, один слот, выбранная квантизация, максимум 400 выходных токенов
для реплики/тега и штатные 1200 у проектного агента, два seed. Полное выполнение
фикстуры и семантика отчёта проверяются отдельно от эвристических `checks`.
Пилот `baseline-default.json` сохраняется для диагностики, а не для итоговой
статистики: в нём две слишком мягкие автоматические проверки отчёта.

Офлайн-проверка самого стенда:

```powershell
python -B -m unittest discover -s benchmarks -p "test_*.py"
```

При выборе победителя сначала сравниваются фактически выполненные поручения,
затем честность и связность ответов, затем задержка. Нельзя засчитывать модельный
«готово» без чтения/изменения фикстуры или выдавать поиск по имитации за настоящий
успешный запрос к поисковику.

## Диагностика Fast-Code Q6_K

Новая загруженная пользователем модель проверяется в её версии Q6_K, а не Q5_K_M.
`--raw-nonthinking --only text` сохраняет те же системные подсказки и историю,
но подаёт ChatML с закрытым блоком thinking через `/v1/completions`. Это отдельный
эксперимент с текстом/тегами: он не проверяет штатные native tool calls и не
меняет настройки Jarvis или LM Studio. Не смешивать его статистику со штатным
`/v1/chat/completions`. Принятые сервером `reasoning_effort: none` и
`chat_template_kwargs` в диагностике не отключили thinking; native `reasoning: off`
отвергнут как недоступный для этой модели.

`--only projects --project-case inventory_fix` запускает один проектный сценарий.
После тайм-аута рабочий поток может временно удерживать общий inference-slot;
сценарий с нулём запросов к модели считается заблокированным стендом, не оценкой
качества модели. Такие сценарии перепроверяются отдельными процессами. Поле
`finish_reason: null` не означает успешное выполнение.

## Пересчёт сохранённых результатов

```powershell
python -B benchmarks/evaluate_results.py logs/model_comparison/baseline.json logs/model_comparison/ministral-q4-text.json
```

Рубрика 3 пересчитывает теги без новых запросов и без изменения исходных JSON:
поиск имени учитывает нормализацию ё/е, как `jarvis_paths.discover`, а поисковый
запрос о GPT Astra 6 должен сохранять номер 6. Для чтения по точному абсолютному
пути нормализация ё/е не применяется. Исходные `checks` в JSON версии 2 остаются
историческими результатами; в новом сравнении все кандидаты оцениваются рубрикой 3.
Эти баллы не проверяют каждый аспект аргументов (например, сохранение ограничения
папкой), смысл отчёта, честность или качество юмора — нужна ручная оценка.

`compact_prompt_probe.py` — дополнительная диагностика: повторяет шесть
разговорных случаев из сохранённого JSON с короткой системной инструкцией,
сохраняя сообщения истории, seed и температуры. Не смешивается с основным
сравнением и не устанавливает эту инструкцию в приложение.

Прогон с суффиксом `cpu` означает загрузку CLI с `--gpu off`: веса не выгружаются
на GPU. Это не гарантирует полного отсутствия GPU-буферов — runtime всё ещё
может оставить offload KV cache. Такой тест остаётся измерением Windows/x86,
а не эмуляцией Orange Pi или прогнозом его точной задержки.

## Повторный раунд: совместимость и факты выполнения

См. `AGENT_RELIABILITY_2026-09-07.md`. Результаты с `evidence-v2` получены после
исправления контекста и отчётов проектного агента; не смешивать их с первоначальным
сравнением как один неизменный эксперимент. Для Gemma применён только её локальный
override шаблона в LM Studio. Глобальная и рабочая модель не переключались.

Адаптер `run_command` теперь возвращает `exit=0/1` перед результатом доверенной
AST-проверки. Это даёт агенту обычный протокол статуса, но по-прежнему НЕ запускает
запрошенную моделью команду. Нулевой код стенда проверяет три искусственных случая,
а не тесты настоящего проекта. Оценка `model_report_complete` — грубая эвристика;
наличие завершённого текста не доказывает выполнение поручения.

`gemma_format_type_argument.jinja` — минимальный helper для наблюдавшейся ошибки
переписанного шаблона. Три офлайн-теста используют Jinja2 (на этом ПК 3.1.4):
отсутствие helper, строковый тип, массив nullable-типов. Это не замена реальной
проверке шаблона LM Studio. Общий offline discovery включает 22 теста.
