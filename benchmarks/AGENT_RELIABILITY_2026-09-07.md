# Jarvis: совместимость инструментов и достоверность отчётов

Второй раунд 7 сентября 2026, после первоначального сравнения моделей.
Рабочая модель `qwen3.8-4b-distill` не заменялась. Новые веса не скачивались;
старые загрузки остались на паузе. Тесты работали только с искусственными
проектами, без настоящих файлов пользователя, сообщений, микрофона и TTS.

## Что было исправлено

### 1. Gemma: ошибка до начала генерации

С обычным диалогом Gemma работала, но любой запрос с `tools` падал на
`format_type_argument`: функция Jinja не определена. Установленный runtime:
`llama.cpp-win-x86_64-nvidia-cuda12-avx2@2.32.0`.

Сравнение шаблона из GGUF с эффективным шаблоном через SDK LM Studio показало:
исходный GGUF не обращался к этому helper, а переписанный сервером шаблон
содержал четыре обращения без определения. Поэтому это была несовместимость
шаблона/интеграции, а не доказательство неспособности модели вызывать инструменты.
Похожая ошибка зарегистрирована в [LM Studio issue #2012](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2012).

Добавлен только отсутствующий helper, без замены всей разметки диалога.
Сначала проверен override одного SDK-запроса, затем создан профиль только Gemma:

```text
C:\Users\user\.lmstudio\.internal\user-concrete-model-default-config\google\gemma-4-E2B-it-qat-q4_0-gguf\gemma-4-E2B_q4_0-it.gguf.json
```

В нём только `llm.prediction.promptTemplate`, пустые параметры загрузки. Рабочий
Qwen, глобальный шаблон, GGUF и конфигурация Jarvis не менялись. После перезагрузки
отдельного экземпляра Gemma обычный `/v1/chat/completions` с `tools` вернул
`finish_reason: tool_calls` и корректный `ping({"value":"test"})`; ping не исполнялся.
Затем прошли реальные многошаговые вызовы чтения искусственных проектов.

Helper сохранён в `gemma_format_type_argument.jinja`; его совпадение с началом
применённого шаблона проверено. Эффективный шаблон до/после — в игнорируемых
`logs/model_comparison/gemma-effective-template-before.json` и `...-fixed.json`.
Настройка шаблона модели описана в [официальной документации LM Studio](https://lmstudio.ai/docs/advanced/prompt-template).
Внутренний путь профиля относится к установленной версии, не является стабильным API.
Для отмены отключите пользовательский шаблон именно Gemma в LM Studio; не меняйте
профили других моделей. После обновления runtime нужно повторно проверить native tools:
сохранённый override иначе продолжит закреплять старый эффективный шаблон.

### 2. Агент перестаёт терять маленький исходник ради журнала

Полный небольшой `read_file` сохраняется приоритетнее списка файлов и пустого EOF.
Перед вытеснением полезного кода уменьшается журнал в запросе. Исходное поручение
не сокращается, пары ID вызов/ответ не разрываются. При 8192 всё ещё действует
лимит 6392 сериализованных UTF-8 байт вместе с инструкциями и схемами инструментов.
Большие проекты по-прежнему требуют выборочного поиска и чтения: весь код не помещается.

Повторное чтение возвращает кэш без повторного I/O и не засчитывается как прогресс.
`next_offset: null`, `eof: true` явно обозначают конец файла. Перед возможной
записью прежний снимок цели инвалидируется, даже если инструмент затем падает.
Наблюдения других файлов сохраняются; произвольный host shell инвалидирует все.
Защита полной перезаписи по полноте чтения и SHA-256 сохранена.

### 3. Факты выполнения отделены от слов модели

Успех `write_file` подтверждается фактическими байтами файла, не строкой «готово».
Итог показывает реальные записи, результаты команд и наличие проверки после
последней записи. Попытка изменения, даже неудачная, инвалидирует старую проверку.
`compile` обозначен как синтаксис без исполнения, а не пройденные тесты приложения.

Эвристика `jarvis_agent_evidence` скрывает явно противоречивые заявления модели;
в рабочем цикле есть одна ограниченная попытка исправить результат. Финальная
аварийная сводка не получает инструментов. Ложное срабатывание на существительные
«изменений»/«исправление» найдено на реальном ответе Qwen и исправлено отдельно.

Границы: хеш доказывает запись байтов, не правильность алгоритма. Нулевой exit
не доказывает полноту тестов. Эвристика не понимает все возможные формулировки,
может пропускать ошибки и консервативно скрыть полезный текст вместе с неверным.
Host shell сохраняет прежние полномочия пользователя и не получает автоматический undo.

## Сравнение на одинаковой версии evidence-v2

RTX 5070 Laptop, контекст 8192, parallel 1, GPU max; два seed на сценарий.
Это Windows/x86, не замер Orange Pi. Веса Gemma — 3 349 516 256 байт,
Qwen2507 Q5_K_M — 2 889 514 080 байт, оба меньше 4 млрд байт.

| Сценарий, ручная оценка | Gemma E2B QAT Q4 | Qwen3-4B-Instruct-2507 Q5 |
|---|---|---|
| Обзор inventory: обе реальные ошибки | 0/2; quantity найден в 1/2 | 1/2; другой итог скрыт защитой |
| Правильное итоговое содержимое total_value | 0/2 | 1/2 |
| Правка плюс запрос успешной проверки после неё | 0/2 | 0/2 |
| Обзор HTML: обнаружен DOM sink в конце | 0/2 | 0/2 |
| Ошибка inference/native-tools | 0/6 | 0/6 |

Gemma в одном обзоре сопоставила README и код, заметила отсутствие quantity,
но не диагностировала StopIteration. При правке повторяла чтение; одна попытка
`write_file` не содержала обязательных аргументов. Реальных записей не было,
а модельные заявления об исправлении в аварийных сводках скрыты.

Qwen в одном обзоре правильно назвала и пропуск quantity, и StopIteration.
В другом сначала выдумала запуск `run_command`, а затем дала неточный ответ о
поиске отсутствующего элемента. Старая широкая эвристика также ошибочно реагировала
на слово «изменений» — это исправлено после данного одинакового прогона.

В первом исправлении Qwen сначала записала верную сумму, затем сама испортила её,
заменив на список произведений. Во втором оставила правильную сумму. Ни в одной
попытке не вызвала проверку после записи, поэтому отчёты имеют частичный статус.
Стенд независимо проверил итоговые байты; модельный текст не засчитывался за правку.

На HTML обе модели не использовали поиск нужного кода. Qwen в обеих попытках
дошла до 19800 из 20363 символов и исчерпала шаги перед блоком JS. Gemma остановилась
раньше. Не засчитываются ни общий пересказ HTML, ни текст «обзор завершён».

Источники: `logs/model_comparison/gemma-evidence-v2-{inventory_review,inventory_fix,site_review}.json`
и `qwen2507-evidence-v2-{inventory_review,inventory_fix,site_review}.json`.
Промежуточные `gemma-template-only-*` (helper без правок агента, по одному seed) и
`gemma-agent-fixed-*` (до адаптивного уменьшения журнала) не смешиваются с таблицей.
Хеши 46 модулей приложения сохранены в каждом основном JSON.

В этом раунде адаптер проверки стенда дополнен префиксом `exit=0/1`.
За ним остаётся доверенная проверка трёх случаев по ограниченному AST; запрошенный
моделью shell/Python не исполняется. Это изменение протокола по отношению к старому
сравнению, не реальный запуск тестов проекта. Автоматический `model_report_complete`
слишком груб для вывода об успехе: незавершённый обзор может получить `true`.

## Итог и оставшаяся работа

### Финальная перепроверка отчёта

После уточнения формулировок защиты повторены четыре попытки Qwen: обзор и
исправление, по два seed (`qwen2507-evidence-final-inventory_review.json` и
`qwen2507-evidence-final-inventory_fix.json`). Это отдельная проверка новой версии,
не подмена цифр таблицы evidence-v2. Полный повтор сайта/Gemma после этой последней
правки эвристики не проводился.

Результат: quantity обнаружена в 2/2 обзорах; корректное объяснение StopIteration
в 1/2. В другом модель всё ещё ошибочно объясняет отсутствие элемента как возврат
«следующего элемента» — речь не стала автоматически достоверной. Рекомендации о
будущих изменениях теперь не скрываются из-за существительных. Заявление о запуске
проверки без соответствующего вызова вызывает корректирующий шаг.

Правильный итоговый файл сохранился в 1/2 исправлений; в обеих отсутствовал запрос
проверки после записи. Теперь явное «поручение выполнено» в этой ситуации скрыто,
а фактическая запись и незавершённая проверка показаны отдельно. Во второй попытке
файл соответствует трём независимым AST-проверкам стенда; это не означает, что
модель сама выполнила проверку или что все тесты приложения пройдены.

### Проверка реализации

Навыки engineering:debug и engineering:testing-strategy задали порядок: сначала
воспроизведение дефекта, затем регрессия, исправление и раздельная оценка модели.
Первые шесть регрессий были красными до изменений. Дополнительный тест с реальным
8K-подобным поручением обнаружил вытеснение кода журналом; ещё два — ошибочную
классификацию существительных и выдуманный запуск команды. Они исправлены.

Финальный полный прогон `python -B run_tests.py`: **23/23 набора проходят**,
включая 52 теста агента, 40 файлового журнала и 33 ответов. Ранее эти три набора
также проверены отдельно: 3/3.
Офлайн-стенд: 22/22 теста (включая три проверки helper Jinja). Первый полный прогон
поймал отсутствие нового модуля в изолированных subprocess-тестах, это исправлено
явной загрузкой зависимости, без ослабления изоляции или отключения тестов.

Хеши всех 46 модулей приложения в финальном Qwen JSON совпадают с текущими файлами.
Из 45 ранее существовавших модулей изменены только `project_agent.py` и
`jarvis_agent_context.py`; добавлен `jarvis_agent_evidence.py`. Остальные прежние
изменения пользователя/предыдущих раундов сохранены. Дополнительно изменены
тесты, адаптер стенда, документация и локальный профиль Gemma. `git diff --check`
для изменённых отслеживаемых файлов ошибок не показал. Логи и полный шаблон
остаются вне Git; новый небольшой helper сохранён в каталоге стенда.

Тестовые экземпляры `jarvis-bench-gemma-fix` и `jarvis-bench-qwen-evidence` выгружены.
Остался только исходный `qwen3.8-4b-distill`, context 20000, parallel 4.
Работников стенда/загрузчика после завершения нет. Веса и старые частичные загрузки
сохранены. Коммит и push не выполнялись.

Совместимость Gemma исправлена, но универсального победителя для управления
проектами пока нет. Qwen показала более полезный анализ и реальную правку, однако
нестабильность и отсутствие проверки не позволяют рекомендовать автопереключение.
Gemma остаётся кандидатом для короткого диалога по первому раунду, не готовым
автономным программистом. Диалог, речь и скорость на плате в этом раунде не измерялись.

Следующий полезный шаг — выбор релевантных файлов/фрагментов и отдельный этап
проверки после записи, затем повторение тех же поручений. Просто увеличивать
лимит шагов или принимать «готово» недостаточно. Проверки на Orange Pi и общая
RAM со STT/TTS остаются отдельной работой.

Python-изменения требуют одного перезапуска Jarvis, когда пользователь будет готов.
Текущий процесс не перезапускался; настройка рабочей модели не менялась.
