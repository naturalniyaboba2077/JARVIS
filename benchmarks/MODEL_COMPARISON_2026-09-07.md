# Подбор модели Jarvis под Orange Pi 5 Pro / 8 ГБ

Результаты раунда, 7 сентября 2026. Рабочая модель и настройки Jarvis не менялись.
Ограничение пользователя — до 4 ГБ на файл весов, в десятичном исчислении.

Дополнение после этого раунда: ошибка инструментов Gemma локализована и исправлена
для её профиля LM Studio; агент получил улучшения контекста и проверки отчёта.
Новые, отдельно измеренные результаты — в [AGENT_RELIABILITY_2026-09-07.md](AGENT_RELIABILITY_2026-09-07.md).
Цифры и ограничения ниже сохранены как исторический исходный прогон.

## Условия

Windows, RTX 5070 Laptop 8 ГиБ, 32 ГиБ RAM. Основной прогон: отдельный экземпляр
модели, контекст 8192, parallel 1, GPU max, два seed. Скорость относится к этому
ПК, а не к Orange Pi. Для реплик выделяется 400 токенов — больше, чем 150 токенов
на некоторых реальных маршрутах Jarvis. Первые данные потока и фрагмент для
озвучки не являются моментом воспроизведения звука.

Навык testing-strategy помог разделить проверку команд, проектного агента и
продолжения диалога. Использованы штатные подсказки Jarvis и вымышленные проекты
с заранее известными дефектами. Модельные команды не исполнялись на компьютере:
теги только разбирались, проектный агент мог менять исключительно фикстуру;
вместо shell применялся ограниченный интерпретатор AST.
Подтверждение пути проверяется как понимание реплики в контексте, а не как
end-to-end тест кнопки UI. Корректный SEARCH-тег не доказывает доступность
поисковика. Ошибки разговора Ministral проверены по самим запросам: история
присутствует, в четырёх просмотренных случаях вход занимает 829–854 токена
при контексте 8192, а не теряется до отправки в модель.

Исходные JSON находятся в `logs/model_comparison/`. Автоматические баллы тегов
пересчитаны единой рубрикой 3 (`benchmarks/evaluate_results.py`): е/ё в поиске
имени эквивалентны, номер модели в поисковом запросе обязателен. В старых JSON
сохранены первоначальные checks. Общего процента успешных поручений нет:
эвристики не заменяют ручную проверку фактических действий и смысла ответа.

## Ministral: ручная оценка

Проверен имеющийся файл из
[lmstudio-community/Ministral-3-3B-Instruct-2512-GGUF](https://huggingface.co/lmstudio-community/Ministral-3-3B-Instruct-2512-GGUF).
Размер 2 146 498 240 байт, SHA-256
`ee46f8f2cc4acf15e89699563e23b4a3919dce2e9ce7c44b53778d6590318e96`
совпал с метаданными Hugging Face. LM Studio загружал пакет с vision-проектором:
каталожный размер пакета 2 986 817 071 байт, это не размер одних текстовых весов.
Оценка CLI для context 8192 / GPU off — 3,40 ГиБ общей памяти модели;
это оценка загрузчика на ПК, не фактический пик RAM Jarvis на плате.

- На вопрос о возможности проверить проект дважды выдаёт исполняемые теги в
  качестве примеров. Стенд их не выполнял; это дефект вывода модели, а не
  свидетельство запуска файлов в настоящем приложении.
- В одном поисковом запросе теряет номер 6. Отчёт/отчет в имени файла не штрафуется,
  поскольку поиск Jarvis сам нормализует ё/е.
- Цвета из истории вспоминает 2/2. Но на вопрос о пароле, которого в контексте нет,
  дважды придумывает пароль. Это синтетический тест, реальные пароли не передавались.
- После явно указанного тайм-аута поиска дважды сочиняет сведения о модели.
- При продолжении отчёта придумывает классы, меню и функции, которых не было в
  переданной истории. Во втором подтверждении пути утверждает, что уже изучает
  элементы сайта, хотя в разговорном сценарии инструментов нет.
- Обзор inventory: 0/2 обнаружений quantity-дефекта; один раз читает код и ошибочно
  утверждает, что next(generator) без default возвращает None при отсутствии имени.
  Эвристический missing_item_bug в этом ответе ложноположителен из-за другого KeyError.
- Правка total_value: 1/2 фактически правильных файлов с сохранением find_equipment.
  Во втором проходе формула исправлена и проверена стендом на трёх наборах данных,
  но сама модель не вызвала проверку. В первом повторяла /inventory.py вместо
  относительного пути и списала свои ошибки аргументов на отсутствие доступа.
- Обзор HTML: 0/2 обнаружений известного DOM-дефекта. В первом прочитано только
  300 из 20 363 символов, во втором опять ошибочные абсолютные пути.
- Слово негдот воспринимает как отдельный термин даже после уточнения анекдот.
  Шутки по моей оценке в основном бессвязны; длинные реплики содержат Markdown,
  хотя подсказка просит его не использовать.

Итого: меньше задержки, но неприемлемое число выдуманных утверждений и
незаконченных действий для самостоятельного помощника.

### Отдельная диагностика короткой инструкции

`ministral-q4-compact-probe.json`: 12 разговорных запросов, та же история и
температуры, заменена только первая системная инструкция. Это не основной балл.
Вымышленные пароли исчезли, однако возникло слишком категоричное утверждение
Вчера не называл вместо Нет в доступной истории. Выдуманная структура проекта
сохранилась, во втором подтверждении пути придуманы открытие Chrome и результаты
проверки HTTPS/скорости. Простое сокращение инструкции проблему не решило.

### Диагностика без GPU-offload весов

`ministral-cpu-text.json`: 21 текстовый сценарий, один seed, Core i7-13620H,
context 8192, parallel 1, CLI `--gpu off`. Теги 7/8 по рубрике 3.
Первый текст — медиана 1,276 с; первый фрагмент для TTS — 1,465 с;
полный разговорный ответ — 11,676 с. GPU-прогон даёт соответственно 0,475,
0,621 и 5,705 с на двух seed. Разная длина сгенерированных ответов тоже влияет
на полное время: это не чистый коэффициент ускорения железа.
Runtime сохранил `offload_kv_cache_to_gpu: true`, поэтому тест нельзя называть
гарантированно полностью CPU-only. Это не эмуляция ARM и не результат Orange Pi.

## Qwen3-4B-Instruct-2507: основной прогон 8192

Скачан файл Unsloth Q5_K_M, 2 889 514 080 байт. SHA-256
`5bde5e9d883622acb02bf77fe7dcbc56a8b9a9ad4be78a72ca23a532658b4ecb`
совпал с публикацией. Загрузка в отдельный экземпляр LM Studio заняла 11,66 с
по CLI, общий контекст 8192; модель работает через штатный OpenAI chat API,
без raw-префикса и без reasoning-effort. В ответах нет скрытого thinking.
48 основных сценариев завершены: 42 текстовых и 6 проектных.

- Теги 14/16. Оба провала — в объяснение с запретом открывать браузер вставлен
  исполняемый `[OPEN:browser]`. Фразу не выполнял стенд; в настоящем Jarvis есть
  дополнительные маршрутизаторы/защиты, поэтому это не доказательство открытия.
- Все 26 разговорных ответов завершены, медиана полного времени 2,030 с.
  Известные цвета воспроизведены 2/2. Неизвестный пароль не придуман, однако
  модель неверно заявляет об отсутствии памяти вообще вместо ограничения контекста.
- После подтверждения пути дважды придумывает проверку сайта, в одном повторе
  даже выдумывает проблему авторизации и обещает её исправлять в режиме без инструментов.
- При продолжении отчёта о проекте не удерживает quantity-находку, придумывает
  контроллеры, функции и другие дефекты. После тайм-аута поиска объявляет продукт
  несуществующим, хотя инструмент не получил источников.
- Обзор inventory: 0/2 реальных обнаружений известных дефектов. Пересказ
  требований README не является обнаружением ошибки. Автоматические 5/6 и 6/6
  в старых checks ложноположительны; второй ответ прямо признаёт, что логику не проверил.
- Правка: 0/2. Оба раза приводит правильную формулу в тексте и сообщает об
  исправлении, но ни разу не вызывает write_file. Фикстура не изменена.
- HTML: 0/2. Оба раза линейно читает 19 800 из 20 363 символов, упирается в 12
  шагов и не доходит до JavaScript. Отчёт частичный; known DOM sink не увиден.
- Юмор по моей оценке слабый: слово негдот превращает в придуманный термин,
  анекдоты часто бессмысленны; использует эмодзи и кавычки вопреки подсказке.

Короткая инструкция, отдельные 12 реплик (`qwen2507-compact-probe.json`),
помогла вернуть quantity-тему в обоих seed, но выдумывание деталей проекта и
необоснованные выводы об отсутствии результатов поиска сохранились.

### Найдено ограничение самого проектного агента

В обоих обзорах inventory перед итоговым запросом уже не было страницы с кодом.
Остались пустая страница offset=175, README и список файлов. Это видно в сохранённых
`requests[-1].messages`, а не только в словах модели. `pack_messages` удаляет
старые группы вызовов по бюджету UTF-8 байтов. При контексте 8192 бюджет равен
6392 байтам (`context_tokens - 1800`), включая инструкции и схемы инструментов;
байты сознательно используются как консервативная верхняя граница числа токенов.
Журнал сохраняет факт чтения и курсор, но не содержание кода или проверенные выводы.

Таким образом, 8K-сравнение измеряет пригодность связки модель + текущий Jarvis,
не чистую способность модели анализировать код. Лишние чтения модели ухудшают
ситуацию, а агрессивное удаление старых данных не позволяет восстановить находки
из журнала. Выдуманные изменения и поисковые выводы этим не оправдываются.
Проверка при 16K проведена отдельно; не включается в общие баллы 8K. Код Jarvis
в этом раунде не изменялся.

Контрольный прогон при 16384, один seed, три отдельные проектные задачи:

- Inventory review: код сохранён в последнем запросе; Qwen уже правильно
  обнаружил пропуск quantity и отметил необработанный случай отсутствия имени.
  Точный тип StopIteration не назван. Автоматический missing_item_bug снова
  неточен — теперь ложноотрицателен. Это поддерживает гипотезу о влиянии
  упаковки контекста, но один повтор не изолирует все эффекты генерации.
- Inventory fix: правку не выполнил. Неверно счёл EOF недостатком доступа к
  полному файлу, хотя total_chars=175 и next_offset=null. Увеличение контекста
  не исправляет понимание метаданных и выполнение команды записи.
- Site review: прочитано 14 400 из 20 363 символов и README. Скрипт в конце
  не прочитан. Сообщение о полном чтении всех доступных файлов противоречит
  журналу, хотя далее модель признаёт, что JavaScript не проверила.

Для 16384 CLI оценил общую память модели в 3,91 ГиБ; это не пик всей системы
на Orange Pi. Загрузка этого экземпляра заняла 34,22 с на данном ПК.

### Дополнительный прогон Qwen с весами на CPU

`qwen2507-cpu-text.json`: один seed, 21 сценарий, context 8192, parallel 1,
CLI `--gpu off`. Теги 7/8; ошибка с OPEN:browser внутри объяснения повторилась.
Все 13 разговорных ответов завершились. Медиана первого текста 2,411 с,
первого фрагмента для TTS 2,861 с, полного разговорного ответа 8,593 с.
Загрузка экземпляра заняла 10,67 с; CLI оценил общую память в 3,35 ГиБ.
Это Windows/Core i7, а не Orange Pi. KV offload остался true, поэтому полностью
CPU-only этот режим не называется. Экземпляр после измерений выгружен.

## Gemma 4 E2B: самый перспективный разговорный кандидат этого раунда

Официальный GGUF Google QAT Q4_0: 3 349 516 256 байт. SHA-256
`fa401b55b07ee70a54c6dae3903c783a6e65064312529ea57175cb5f8dec6634`
проверен целиком после скачивания. Загружены только текстовые веса, без mmproj
и MTP. Идентификатор каталога LM Studio — `gemma-4-e2b-it-qat`.
Загрузка отдельного GPU-экземпляра заняла 7,63 с. CLI оценивает общую память
при 8192 / GPU off в 3,37 ГиБ, что не является измерением RSS всей системы.

### Текст, диалог и теги

- 15/16 тегов, все 26 разговорных ответов завершены без скрытого thinking.
  Медиана первого текста 0,471 с, первого фрагмента для TTS 0,552 с,
  полного разговорного ответа 1,032 с, полного ответа с тегом 0,598 с.
- Один раз дописала OPEN:browser после объяснения браузера вопреки запрету его
  открывать. Во втором повторе этого не было. Это остаётся существенной ошибкой.
- Цвета из истории 2/2. Вопрос о пароле без данных не привёл к выдумыванию пароля,
  но объяснение про отсутствие доступа к истории слишком общее для Jarvis с памятью.
- В продолжении проекта сохранила тему количества в обоих повторах. При этом
  фразы «проект функционален» и «структура логична» шире реально проверенного.
- Подтверждение пути поняла, но вместо продолжения поручения спрашивает, что
  проверять в первую очередь. Выдуманного завершённого аудита в этих двух ответах нет.
- После тайм-аута поиска не сочинила характеристики GPT Astra 6. Объяснения
  неточны: спекулирует о новой/закрытой информации или заявляет об отсутствии
  прямого интернета вместо конкретного тайм-аута инструмента.
- Понимает «негдот» как анекдот, но часто задаёт лишний вопрос о теме. Юмор по
  моей оценке пока слабый, часть анекдотов бессмысленна. Во втором повторе есть
  уместный подкол про прошивку старого процессора и ответ про очередь звонков.
  Переход к серьёзному ответу о резервной копии выполняет в обоих повторах.
  В одном длинном анекдоте остаются кавычки.

### Проектные задачи: блок совместимости, а не оценка кода

Во всех шести попытках (review/fix/site × два seed) первый запрос с `tools[]`
отвергнут LM Studio: `Error rendering prompt with jinja template: Cannot call
something that is not a function: got UndefinedValue`. Ошибка возникает до
первого токена. Дальше агент получает только обычное текстовое резюме без tools;
код фикстуры не прочитан моделью, запись и проверка не происходят.

Отдельный дефект достоверности всё же наблюдается в аварийных резюме: во втором
inventory_fix Gemma пишет «изменения внесены», хотя write_file не было. В обзорах
сайта оба раза придумывает просмотр структуры HTML. Агент дописывает честную
пометку о том, что код не прочитан, но это не устраняет противоречие в тексте.
Следовательно, более аккуратный короткий диалог не гарантирует честного отчёта
об исполнении, особенно после ошибки инструмента.

Поэтому нельзя заключить, что Gemma не способна находить или исправлять дефект:
штатная интеграция не дала ей начать. Но и рекомендовать её как готового
автономного исполнителя в нынешнем Jarvis нельзя.

В [трекере LM Studio](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2012)
есть сходная ошибка шаблона другой Gemma. Это не доказательство той же причины:
в проверенном локальном GGUF наш шаблон имеет 18 567 символов и вообще не
вызывает упомянутый там `format_type_argument`. Конкретная строка активного
шаблона LM Studio пока не локализована. Весовой файл исправен, а обычный чат
работает; менять веса или глобальный шаблон по чужому issue без проверки нельзя.

### Дополнительный прогон Gemma с весами на CPU

`gemma-e2b-cpu-text.json`: один seed, 21 сценарий, context 8192, parallel 1,
CLI `--gpu off`. Теги 8/8, все 13 разговорных ответов завершены. Медианы:
первый текст 1,345 с; первый фрагмент для TTS 1,505 с; полный разговорный ответ
3,475 с. Загрузка экземпляра заняла 6,01 с. Это диагностический прогон x86,
не прогноз задержки Orange Pi и не гарантия полностью CPU-only при KV offload.
Цель «первый звук за секунду» этим измерением не подтверждена.

  официальная non-thinking версия. Квантизация Unsloth Q5_K_M, 2 889 514 080 байт.
  Скачана и протестирована в этом раунде.
- [Google Gemma 4 E2B QAT Q4_0](https://huggingface.co/google/gemma-4-E2B-it-qat-q4_0-gguf):
  официальные GGUF-веса после quantization-aware training, 3 349 516 256 байт.
  Скачана и протестирована; мультимодальный проектор не скачивался.
- [LFM2.5-1.2B-Instruct](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct):
  отсеяна по карточке до загрузки. Русский отсутствует в списке поддерживаемых
  языков, программирование авторы не рекомендуют. Это не результат нашего теста.
- Phi-4-mini-instruct и Qwen3.5-2B оставлены как резервные направления,
  не скачиваются параллельно текущим приоритетам и не считаются протестированными.

## Выбор и следующий шаг

Готового универсального победителя нет. Для дальнейшей адаптации первым выбрал
бы Gemma E2B: лучший результат тегов и более аккуратное продолжение диалога в
этом небольшом наборе, но необходимо исправить и перепроверить native tools.
Qwen2507 — резерв с работающим нативным API и низкой задержкой, однако нельзя
принимать его «исправил» за факт без подтверждённой записи и проверки результата.
Ministral выигрывает размером, но проигрывает достоверностью. Fast-Code пока
не подходит для штатного быстрого ответа из-за thinking/интеграции.

Следующий полезный этап — совместимость инструментов Gemma, сохранение важных
фрагментов/выводов проектного агента и обязательная проверка заявлений о правках.
Эти изменения не выполнялись в рамках поиска моделей. Продолжение бесконечной
загрузки похожих весов само по себе не устранит обнаруженные проблемы Jarvis.

Для Orange Pi отдельно нужны первый звук, tokens/s, пик RSS всей системы,
STT/TTS вместе с LLM и троттлинг. Размер GGUF менее 4 ГБ ещё не доказывает,
что вся система стабильно работает в 8 ГБ и отвечает голосом за секунду.
