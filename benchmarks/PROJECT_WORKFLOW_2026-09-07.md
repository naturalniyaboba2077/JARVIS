Дата: 7 сентября 2026. Проект: `C:/Users/user/Documents/Jarvis`.
Выполнены пункты 1–3 согласованного плана. Пункт 4 — Orange Pi и измерения на
плате — исключён по просьбе пользователя. Новые модели не скачивались.

Итог: в этом небольшом наборе **Distill лучше сохранила правильные правки**
(6/6 против 5/6 Qwen2507 и 4/6 Gemma), но заметно медленнее в разговоре.
Универсальной замены, надёжной во всех поручениях, не обнаружено. Рабочую модель
не менял. Сначала стоит исправлять провалы контекста/подтверждений в приложении,
а не полагаться только на замену GGUF.

## Изменения приложения

- `jarvis_project_map.py`: ограниченная карта исходников/символов, README,
  точек входа и тестов. Подготовка реального участка кода до первого запроса.
  HTML с 420 декоративными строками больше не приходится читать с начала,
  чтобы добраться до script. Это выбор фрагментов, не полный аудит проекта.
- `replace_text`: точечная версионированная замена прочитанного уникального
  фрагмента. Сохранение остального файла, защита хешем и CAS под блокировкой,
  поддержка LF в аргументах при однородных Windows CRLF в исходнике.
- `jarvis_project_verify.py`: проверку после записи инициирует приложение,
  а не модель. Синтаксис отделён от поведения; фиксированные команды для
  unittest/pytest/Node, замороженный набор тестов, лимиты и отмена.
- `jarvis_agent_evidence.py`: результат проверки привязан к ревизии правки;
  новая операция делает старый результат недействительным. Отсутствие тестов
  не приравнивается к успеху. Подробный контракт — в `PROJECT_AGENT_FIXES.md`.

Реальные тесты проекта выполняются только в режиме изменений, с правами
пользователя, НЕ в песочнице. Окружение — Python Jarvis и Node из PATH; чужая
venv не активируется, зависимости автоматически не устанавливаются. Произвольный
host shell сохраняет прежнюю политику и не получает гарантий версионированной
записи/undo. В режиме обзора поведенческого исполнения и записей нет.

## Проектные результаты

Дроби — успешные попытки из двух. «Исправление» ниже означает правильный итоговый
код на заданных входах, неизменность соседнего кода/файлов и автоматическую
проверку. Оно НЕ требует красивого завершённого отчёта: это отдельный показатель.
Находки в обзорах сверены чтением ответов, а не только булевыми checks.

| Поручение / показатель | Qwen2507 | Gemma E2B | Distill |
|---|---:|---:|---:|
| Исправить price × quantity, не менять другую функцию | 2/2 | 0/2 | 2/2 |
| Исправить скидку в длинном файле, сохранить комментарии | 1/2 | 2/2 | 2/2 |
| Исправить average для пустого и непустого списка | 2/2 | 2/2 | 2/2 |
| Итого исправления с сохранностью соседнего кода | 5/6 | 4/6 | 6/6 |
| Из них без частичного статуса итогового отчёта | 5/6 | 0/6 | 4/6 |
| В обзоре названы обе ошибки inventory | 2/2 | 1/2 | 2/2 |
| В HTML названы риск innerHTML и безопасная замена | 0/2 | 0/2 | 1/2 |
| Во вложенном JS названы риск и textContent | 2/2 | 2/2 | 1/2 |

Важные детали:

- Qwen математически исправил все 6/6 примеров, но в одном проходе скидки затем
  изменил комментарий вне необходимой правки. Четыре арифметические проверки
  оставались зелёными; отдельная проверка сохранности заметила нарушение.
  Прошедшие тесты не доказывают выполнения ВСЕХ ограничений поручения.
- Gemma не записала inventory ни разу; вместо правки перечитывала EOF, затем
  печатала неподдерживаемый TOOL_REQUEST в аварийном отчёте. Эти строки не
  исполнялись. Скидку/average она исправила, но после этого зацикливалась.
- Gemma inventory, второй seed: raw `missing_item_bug=true` — ложноположительная
  оценка. В ответе функция ошибочно названа корректной; найден только quantity.
  В таблице это исправлено вручную на 1/2. Во вложенном JS второй ответ Gemma
  содержит противоречивые объяснения, хотя риск и замена названы.
- Distill сохранила все шесть исправлений, но дважды потеряла связность отчёта
  после успешной записи. Во втором HTML-проходе не получила законченный ответ
  в отведённом окне. В обзоре inventory добавила ложное сомнение в `sum([])`.
- Distill в первом вложенном JS выдумала TypeError от присваивания null в
  innerHTML существующего элемента. Отдельная доверенная проверка DOM в jsdom
  подтверждает: null/число присваиваются без этого исключения. Указание XSS в
  другом ответе не доказывает работоспособность предложенного моделью PoC.
- Все 6 HTML-попыток получили script после длинного префикса. Значит, прежнее
  недочитывание устранено для этой фикстуры, но знание кода моделями не гарантировано.

Фрагменты кода без обратных кавычек/ограждений могут терять кавычки при нынешнем
оформлении отчёта через plain_reply. Это ограничение отображения, не обязательно
ошибка исходного ответа модели. Записи инструментов и файлы проверялись отдельно
по байтам; их этот форматтер не изменяет.

Почему непустой ответ не считается успехом:

- Qwen дважды вывел OPEN:browser при явном «не открывай». В продолжении разговора
  выдумал структуру и успешную проверку проекта; при отказе один раз придумал
  C:/Projects/Magazine/Current. Это модельные теги/реплики, не исполненные действия.
- Gemma лучше обработала отказ и вопрос про average, но один раз тоже вывела
  запрещённый OPEN. Вместо известного дефекта проекта переходила к выдуманным
  интеграциям. В сравнении источников потеряла ссылки, один раз перепутала экспорт
  с импортом. Сухая вежливость ещё не равна требуемому пользователем юмору.
- Distill на отказ от архивного проекта дважды начала сочинять новый проект,
  дошла до лимита 400 токенов. Музыку один раз заменила браузером, другой —
  несуществующим кириллическим тегом. При поиске файла выдумала C:\\Documents,
  а при чтении изменила точное имя. В одном ответе неверно приравняла тайм-аут
  поиска к отсутствию страниц в базе; в другом придумала сведения о GPT-4.5.
- Ни одна модель не выполнила новое сравнение источников полностью. Поэтому
  умение генерировать SEARCH само по себе не доказывает умение прочитать и
  корректно пересказать результат поиска.
- По моей оценке прочитанных юмористических реплик, стабильного связного
  остроумия нет у всех трёх. Автоматическая проверка не измеряет, смешна ли шутка.

Практический выбор: сохраняю текущую Distill, не включаю автоматическую замену.
Если важнее скорость коротких ответов, Gemma — кандидат для отдельного
разговорного маршрута, но не подтверждённая универсальная модель. Qwen2507 быстрее
Distill и лучше Gemma завершает правки в этом наборе, однако нарушил сохранность
комментария и хуже обработал отклонение проекта. Двух seed недостаточно для
широкого рейтинга; контроль действий и структурированное состояние диалога нужны
независимо от выбора модели.

## Регрессии и границы результата

- Полный Python runner: 24/24 набора.
- Новый workflow: 31 тест, 30 выполнены успешно, 1 пропущен из-за отсутствия
  pytest. Реальные доверенные unittest и Node прошли. Ветки ошибок, отмены,
  нулевых тестов, изменения тестов, конфликта записи и лимита вывода проверены.
- Отдельный offline-стенд: 26/26 тестов. UI DOM: 51/51.
- git diff --check: без ошибок; имеются прежние предупреждения Git о CRLF/LF
  в посторонних файлах, их нормализация не выполнялась.

Нельзя утверждать, что теперь Jarvis безошибочно выполняет любые поручения.
Реализован более проверяемый цикл работы. Выборка маленькая; полностью автономный
рефакторинг большого проекта, end-to-end поиск/голос и работа на плате не доказаны.
Перенос пользовательских файлов и настройки доступа к дискам не изменялись.

После завершения все три собственных тестовых экземпляра выгружены. В LM Studio
остался только исходный qwen3.8-4b-distill, context 20000, parallel 4, idle.
Приложение не перезапускалось; новые Python-файлы подхватятся при следующем
запуске. Это не отменяет горячее применение пользовательских настроек.
Коммит/push не выполнялись; существующие изменения пользователя сохранены.
