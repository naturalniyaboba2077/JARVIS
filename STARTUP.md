# Быстрый запуск Jarvis

Обычный ярлык и команда `python jarvis.py` теперь сначала открывают окно,
а затем подключают тяжёлое ядро в фоне. Переустанавливать ярлык не требуется.
Чтобы применить изменения, закройте старый Jarvis крестиком и запустите снова.

## Что измерено на этом ПК

| Замер | Результат |
| --- | --- |
| До изменения: процесс с `import jarvis` и профилированием импортов, ещё до создания окна | 9,69 с |
| После изменения: импорт загрузчика, UI и webview без ядра | 0,14 с |
| Появление настоящего нативного окна, три отдельных процесса | 0,945 / 0,949 / 0,788 с |
| HTML, JavaScript, поле команды и мост к Python готовы | 2,031 / 1,759 / 1,400 с |

Повтор после финальных исправлений: окно **0,711 / 0,960 / 0,940 с**,
интерфейс **1,426 / 1,980 / 1,708 с**. Полный изолированный прогон прошёл:
18/18 наборов Python (включая 15 новых проверок запуска) и 35/35 DOM-проверок.

Это замер **от запуска процесса до появления интерфейса**, не время первого
ответа. Проверочные окна используют настоящий HTML/CSS/JS и WebView2, но
синтетический мост: не включают микрофон, не отправляют запросы модели, не
запускают напоминания и интеграции. На холодном старте после перезагрузки ОС
или при высокой нагрузке результаты могут отличаться.

## Поведение при старте

- Можно сразу набрать команду, закрыть, свернуть или развернуть окно.
- До готовности командного цикла отправка заблокирована. Черновик сохраняется;
  автоматической отправки после загрузки нет.
- Внизу виден текущий этап загрузки и прошедшее время, без выдуманных процентов.
- Настройки, открытые при запуске, загружаются после готовности ядра. Пустые
  значения до загрузки не могут перезаписать конфигурацию.
- Если ядро не загрузилось, интерфейс показывает ошибку, а не вечную готовность.
- Готовность командного цикла не доказывает, что STT/LLM/TTS уже прогрелись.
  Первая некэшированная реплика может потребовать дополнительного времени.

## Реализация

`jarvis.py` перед тяжёлыми импортами передаёт запуск в `jarvis_bootstrap.py`.
Загрузчик использует событие `window.events.loaded`: обычный
`webview.start(run_assistant)` начинает фоновую функцию ещё **до** создания
нативного окна и не обеспечивает нужного порядка.

Мост `StartupApi` содержит только явные методы прежнего `JarvisApi`. Во время
старта он отдаёт статус и управляет окном; ранние команды не накапливаются и
не воспроизводятся. После импорта подключается тот же командный цикл. Закрытие
до или во время импорта запрещает последующий запуск помощника.

Подготовка речевого кэша всех движков вынесена из командного цикла в один
фоновый поток. Существующие файлы кэша индексируются до загрузки Piper;
его загрузка и синтез синхронизированы, чтобы прогрев и первый ответ не
создавали две модели и не получали частично загруженный голос. При текущей
озвучке необязательное заполнение кэша прекращается. Настройки голоса не меняются.

Убраны неиспользуемые импорты Google API, DDGS и ImageGrab из ядра и раннее
сканирование памяти Obsidian: память по-прежнему читается через существующий
кэш по запросу. Маршрутизация, права на файлы, подтверждения и выбранная модель
не изменены.

## Повторная проверка

Используйте установленный Python с зависимостями приложения, не пустую `.venv`:

```powershell
cd C:\Users\user\Documents\Jarvis
& "$env:LOCALAPPDATA\Programs\Python\Python310\python.exe" -B jarvis_startup_check.py --runs 3
& "$env:LOCALAPPDATA\Programs\Python\Python310\python.exe" -B run_tests.py
node --test ui/test-ui.cjs
```

Первый скрипт кратко открывает и закрывает три тестовых окна. Каждый запуск
проверяет наличие поля ввода, ненулевую ширину интерфейса, JavaScript и мост.
Для дочернего процесса установлен предел 20 секунд; чужие окна не закрываются.
Это явная проверка по запросу, не фоновый автозапуск и не предварительно
запущенный скрытый помощник.

В `logs/jarvis_ГГГГ-ММ-ДД.log` реальные этапы отмечены `[BOOT]` с PID:
`window_shown`, `interface_loaded`, `core_imported`, `command_loop_ready`.
Проверочные окна используют `[BOOT-CHECK]`. В обычном запуске отсчёт идёт от
входа в `jarvis.py`; проверочный скрипт включает также запуск дочернего Python.
Время прогрева конкретного движка смотрите отдельно в записях LLM/STT/TTS.
Логи могут содержать личные данные: они не добавляются в Git и не отправляются.
